# bins BDD living documentation implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `subagent-driven-development` (recommended) or `executing-plans` to implement
> this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first Dots BDD/Gherkin lab for `config/bin` with minimal
guide docs, executable Cucumber features, mise tasks, and a handoff prompt.

**Architecture:** `assets/specs/bin` owns SDD artifacts.
`assets/features/bin` owns executable Gherkin and TypeScript step
definitions. Root `mise.toml` is the user-facing task entry point for BDD,
Gherkin linting, and `xc` checks.

**Tech Stack:** Markdown, Gherkin, `@cucumber/cucumber`, `@cucumber/screenplay`,
`tsx`, TypeScript, Bun, Node 22 through mise, `gherkin-lint`, zsh, shellcheck,
VS Code/Cursor Cucumber extension.

# Dots BDD and Gherkin guide

Dots uses Gherkin to describe user-visible command behavior. The first living
documentation suite covers `config/bin`.

## Rules

- Write one behavior per scenario.
- Use third person and present tense.
- Keep most scenarios to three to five steps.
- Use one main `When` per scenario.
- Use real command names and real expected output.
- Use `Rule` to group scenarios by command behavior.
- Use `Background` only when every scenario needs the same context.
- Keep terminal mechanics, fzf key navigation, and implementation details out of
  the first read-only slice.
- Do not use placeholder rows or fake command names.

## Good example

```gherkin
Feature: Discover xc commands

  Rule: The launcher lists available tools

    Scenario: User lists tools from the fixture bin directory
      Given the fixture bin directory contains executable xc tools
      When Alice runs `xc list`
      Then Alice sees the command succeed
      And Alice sees "xc-sample" in the output
      And Alice sees "Fixture tool" in the output
```

## Bad example

```gherkin
Scenario: User presses arrows in fzf
  Given the terminal is focused
  And fzf has rendered rows with ANSI colors
  When arrowDown has been pressed many times
  Then the scroll offset changes
```

This is a later integration concern, not the first read-only bins slice.
```

# Dots testing guide

Dots uses focused checks. For the bins BDD pilot, Cucumber verifies living

## Cucumber, Screenplay, and Bun

Cucumber-JS is a Node runner. Bun is still the package manager and command
launcher, but the runner and step definitions must resolve the same local
`@cucumber/cucumber` dependency.

Use a minimal private root `package.json` for dev dependencies only. Do not add
package scripts. Root `mise.toml` owns every repeatable command.

Required dev dependencies:

```sh
bun add --dev @cucumber/cucumber@^10 @cucumber/screenplay tsx gherkin-lint
```

Use Node 22 through mise for BDD tasks. `@cucumber/screenplay` currently peers
with Cucumber-JS through version 10, so this pilot pins Cucumber 10 instead of
floating to the latest Cucumber-JS release.

Required Cucumber command shape:

```sh
bun install --frozen-lockfile
bunx cucumber-js \
  assets/features/bin/**/*.feature \
  --require-module tsx/cjs \
  --require assets/features/bin/step_definitions/support/**/*.ts \
  --require assets/features/bin/step_definitions/**/*.steps.ts
```

The optional `bunx --bun cucumber-js` path can be tested later for speed, but
it is not the required path for the bins pilot.

## Screenplay model

Keep Cucumber step definitions thin. Steps translate Gherkin into actor
activities and questions:

- Actors represent terminal users.
- Tasks express command-level intent, such as listing available commands.
- Interactions run shell commands with controlled environment variables.
- Questions inspect observable results, such as exit code and stdout.

## Layers

| Layer            | Purpose                       | Command                                      |
| ---------------- | ----------------------------- | -------------------------------------------- |
| Gherkin lint     | Validate `.feature` style     | `mise run docs:gherkin:lint`                 |
| Cucumber dry run | Verify step binding           | `mise run docs:bdd:dry-run`                  |
| Cucumber run     | Execute living docs           | `mise run docs:bdd`                          |
| Bun specs        | Existing command-level checks | `mise run xc:specs` and focused `xc-*` tasks |
| Shell syntax     | Validate changed zsh scripts  | `zsh -n <script>`                            |
| Shell lint       | Lint changed zsh scripts      | `mise exec -- shellcheck <script>`           |
| Whitespace       | Catch trailing whitespace     | `git diff --check`                           |

## Advanced BDD tools

Use Screenplay in the first bins suite. Do not add Serenity/JS, CodeceptJS,
Explorbot, or AI testing tools during the first bins pilot. Keep them as
research references for later browser, cross-interface, or reporting-heavy
specs.

## Rule

Every task must finish with its listed gate green before the next task starts.
```

# Dots config/bin guide

This guide captures practical conventions used by `config/bin`. It is not a
general shell guide, a shell architecture manifesto, or a repo-wide shell
cleanup plan.

## Conventions

- Use `zsh` for `config/bin` tools.
- Keep public help in `##?` docopt-shaped comments.
- Use `xc-usage` for help extraction when a tool supports it.
- Keep commands executable from a non-interactive shell with explicit
  arguments.
- Do not source personal shell config.
- Prefer explicit environment variables in tests and features, such as
  `XC_BIN_DIR` or `FABRIC_PATTERNS_DIR`, instead of depending on a personal
  `PATH`.
- Check optional dependencies near the command boundary and print a clear
  human-readable error before exiting non-zero.
- Keep read-only listing output deterministic. Prefer raw output modes for
  executable specs when a command supports them.
- Add checks as mise tasks, not hidden scripts.

## Verification

Use the focused gate for the changed tool:

```sh
mise run xc:specs
mise run xc-fabric:specs --scenario ls_raw
mise run xc-usage:specs
```

When zsh files change, also run:

```sh
mise exec -- shellcheck <changed-zsh-scripts>
zsh -n <changed-zsh-scripts>
git diff --check
```
```

# REQUIREMENTS: bins BDD living documentation

## Overview

Create the first Dots living documentation suite for `config/bin`. The suite
starts with read-only `xc` and `xc-fabric ls` behavior.

## User roles

- Terminal user: runs `xc` and `xc-*` commands.
- Maintainer: changes `config/bin` scripts and needs fast verification.
- Agentic worker: follows specs, tasks, and handoff prompts.

## Requirement 1: Minimal guides

**User story:** As a maintainer, I want shared Dots BDD guide docs so
future specs use shared language without copying generic guidance.

**Acceptance criteria:**

1. WHEN reading `assets/guides/GLOSSARY.md` THEN it SHALL define Dots,
   Guides, Spec, Living documentation, Feature file, Scenario, Step
   definition, `config/bin`, `xc-*` tool, `xc` launcher, `xc-usage`, Mise task,
   and Acceptance gate.
2. WHEN reading `assets/specs/bin/CONFIG_BIN_GUIDE.md` THEN it SHALL state that
   Functional Core, Imperative Shell is not the `config/bin` architecture.
3. WHEN reading `assets/specs/bin/SKILL.md` THEN it SHALL route bins SDD
   artifacts to `assets/specs/bin` and executable Gherkin to
   `assets/features/bin`.

## Requirement 2: Gherkin suite location

**User story:** As a maintainer, I want feature files under a conventional
features tree so Cucumber tooling can discover them easily.

**Acceptance criteria:**

1. WHEN the bins Cucumber suite is created THEN `.feature` files SHALL live
   under `assets/features/bin`.
2. WHEN step definitions are created THEN TypeScript steps SHALL live under
   `assets/features/bin/step_definitions`.
3. WHEN command execution support is created THEN it SHALL use Screenplay
   actors, activities, and questions instead of direct world helper methods.
4. WHEN `assets/specs/bin` is updated THEN it SHALL contain SDD artifacts,
   not `.feature` files.

## Requirement 3: Command discovery living docs

**User story:** As a terminal user, I want to list available `xc-*` tools so I
can discover commands without memorizing them.

**Acceptance criteria:**

1. WHEN the fixture bin directory contains executable `xc-*` tools AND the user
   runs `xc list` THEN the command SHALL exit 0.
2. WHEN `xc list` succeeds THEN stdout SHALL include `xc-sample`.
3. WHEN `xc list` succeeds THEN stdout SHALL include `Fixture tool`.
4. WHEN `xc -h` runs THEN stdout SHALL include `xc`, `list`, and `launcher`.

## Requirement 4: Fabric listing living docs

**User story:** As a Fabric user, I want to list available Fabric patterns so I
can choose a pattern before running it.

**Acceptance criteria:**

1. WHEN fixture Fabric patterns exist AND the user runs `xc-fabric ls --raw`
   THEN the command SHALL exit 0.
2. WHEN `xc-fabric ls --raw` succeeds THEN stdout SHALL include `summarize`.
3. WHEN `xc-fabric ls --raw` succeeds THEN stdout SHALL include
   `youtube_summary`.

## Requirement 5: Mise-only execution

**User story:** As a maintainer, I want all BDD and bins checks available as
mise tasks so there are no hidden runner scripts.

**Acceptance criteria:**

1. WHEN reading root `mise.toml` THEN it SHALL expose `docs:gherkin:lint`,
   `docs:bdd:dry-run`, and `docs:bdd`.
2. WHEN reading root `mise.toml` THEN it SHALL expose the `xc` checks used by
   the bins pilot or delegate to the existing `config/bin` tasks.
3. WHEN searching the repo for new BDD runner scripts THEN none SHALL exist
   outside Cucumber TypeScript step definitions.
4. WHEN reading root `package.json` THEN it SHALL contain dev dependencies only
   and no `scripts` block.
```

Create `assets/features/bin/step_definitions/support/screenplay/run-command.ts`:

```ts
import { spawnSync } from "node:child_process";
import type { Actor, Action } from "@cucumber/screenplay";

export type CommandResult = {
  readonly exitCode: number | null;
  readonly stdout: string;
  readonly stderr: string;
};

type CommandEnvironment = Record<string, string | undefined>;

export const RunCommand = {
  with(command: readonly string[], env: CommandEnvironment = {}): Action {
    return (actor: Actor) => {
      const result = spawnSync(command[0], command.slice(1), {
        encoding: "utf8",
        env: {
          ...process.env,
          ...env,
        },
      });

      actor.remember("lastCommand", {
        exitCode: result.status,
        stdout: result.stdout,
        stderr: result.stderr,
      } satisfies CommandResult);
    };
  },
};
```

Create `assets/features/bin/step_definitions/support/screenplay/last-command.ts`:

```ts
import type { Action, Actor } from "@cucumber/screenplay";
import type { CommandResult } from "./run-command";

const lastCommand = (actor: Actor): CommandResult => {
  return actor.recall<CommandResult>("lastCommand");
};

export const LastCommand = {
  exitCode(): Action<number | null> {
    return (actor: Actor) => lastCommand(actor).exitCode;
  },

  stdout(): Action<string> {
    return (actor: Actor) => lastCommand(actor).stdout;
  },

  stderr(): Action<string> {
    return (actor: Actor) => lastCommand(actor).stderr;
  },
};
```

  actor.attemptsTo(
